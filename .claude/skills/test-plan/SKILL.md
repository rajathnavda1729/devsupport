# Test plan

> **Workspace:** `<ws>` is this feature's folder in the target repo. Get it with `python3 devkit/tools/scaffold.py where <slug>`. Its documents are grouped: `01-requirements/`, `02-design/` (`decisions/`, `reviews/`), `03-delivery/`, `04-quality/`. Write only there.
>
> **Format contract:** fill in the document that `scaffold.py` created from its template. Never write a document from scratch. Keep these:
> - the `<!-- devkit:doc … -->` marker line;
> - the H1 prefix;
> - the header fields;
> - every H2 section, in its order;
> - the table columns;
> - the mermaid blocks the template has.
>
> Put extra detail under `###`. Write "None" or "N/A — reason" for an empty section. A missing document comes from `scaffold.py doc <slug> <type>`. The lint hook checks every write. Before you finish, run `python3 devkit/tools/doclint.py --feature <slug>`.

**Input:** `01-requirements/requirements.md` (acceptance criteria, critical items, NFRs), `02-design/lld.md` (error table, state machines, API contracts)
**Output:** `<ws>/04-quality/test-plan.md`, plus `traceability.md` generated by the tracker.

## Deriving test cases
For each requirement, derive cases with these techniques:
- **Acceptance criteria.** Each Given/When/Then becomes at least one case.
- **Equivalence partitions and boundaries.** Test min, min−1, max and max+1, empty, null and huge inputs.
- **Negative cases.** Cover invalid input, unauthorised and forbidden users, conflicts and duplicates.
- **State transitions.** Every valid transition gets a case, and so does at least one invalid transition per state machine.
- **Error table.** Every row of the LLD error-handling table gets a case.
- **CRITICAL requirements.** Each needs at least one positive case, one negative case, and one failure-injection case: kill the dependency, time it out, or send a duplicate request.
- **NFRs.** Write a case in §6 that points to its benchmark scenario (`04-quality/benchmark-plan.md`) or other verification.

## Format
One row per case in the §5 table. **The ID must be the first cell** and the *Requirements* cell must list the FR/NFR IDs, because the tracker parses these.
`| TC-001 | Create link happy path | FR-001 | Functional | P0 | … | … | … | yes | Not run |`
- Priority: P0 for critical paths and CRITICAL requirements; P1 for Must; P2 for Should; P3 for Could.
- Automated? is `yes` (with the test file or function name, once known), `no`, or `planned (T-xxx)`.

## Steps
1. Fill in the scope, strategy, environments, and the entry and exit criteria.
2. Derive and write the cases.
3. Run `python3 devkit/tools/tracker.py -f <slug> trace` to write `traceability.md`, then `... validate`. Every CRITICAL requirement must show both a task and a test. Add cases until validate shows no errors.
4. If automation tasks are missing from the tracker, add them (`type: test`, linked to the TC and requirement IDs).
5. Report the case counts by priority and type, the coverage %, and any requirement without a test.
6. **After the tests are executed**, which may be later, create the report with `python3 devkit/tools/scaffold.py doc <slug> test-report`. Fill it in from the real results only: test names, `bench.py` result files, and the logwatch report. Every TC gets a Pass, Fail, Blocked or Not run status.
