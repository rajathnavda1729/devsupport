# Architecture decisions (ADRs)

- **Know the decisions before designing.** Before solutioning, HLD or LLD work, run `python3 devkit/tools/adr.py scan` and `adr.py search <keywords>`, and read the relevant ADRs.
- **Accepted ADRs are binding.**
  - A design may comply with one, or replace it through a new ADR created with `--supersedes <n>`, after the user explicitly approves.
  - Silently contradicting an Accepted ADR is a blocking design-review finding.
- **ADRs are immutable records.**
  - Only the status and links of an existing ADR change, through `adr.py set-status` and `adr.py supersede`.
  - To change a decision, write a new ADR. Never delete or renumber one.
- **Respect the repo's existing ADR format.** Existing ADRs keep their format (Nygard, MADR …). Devkit only creates new ADRs, from `devkit/templates/adr.md`, with `adr.py new`, which follows the repo's file naming and uses global numbering.
- **Placement.** Repo-wide decisions go in the repo decisions dir. Decisions internal to one feature go in `<ws>/02-design/decisions/` (`--feature <slug>`).
- **Only the user accepts decisions.** New ADRs start `Proposed`; the user moves them to `Accepted`. Retroactive ADRs, which document decisions already in force, are created only after the user confirms them, and must cite code evidence.
- `decision-log.md` and `decision-log.json` are generated by `adr.py scan`. Never edit them by hand.

**Why:** prior decisions encode constraints and lessons. Designs that ignore them create inconsistency, and decisions that change silently leave nobody knowing which rule applies.
